** Overview

This phase installs application sandboxing infrastructure using bubblewrap to isolate untrusted code from sensitive credentials, and provides the **sandboxed remote-access landing zone** that lets you operate the box from a laptop-side Claude over WireGuard without exposing the box's secrets.

**Two SSH principals, selected by which uid you land as** (enforced on the box, not by trusting the agent):

- =ops= — the sandboxed crypto-ops front door, **default ON** (`ops_access_enabled`). The laptop connects as =ops@box= over wg0 and lands in a bubblewrap =ForceCommand= jail running as a non-privileged uid with no sudo. The real wall is **uid separation**: =ops= cannot read keys another uid owns at =0700=. Bubblewrap is defense-in-depth — it blanks the secret paths and narrows the filesystem. No on-box Claude is installed for this mode; Claude runs on the laptop.
- =dev= — full on-box contributor access, **default OFF** (`dev_access_enabled`). When enabled, installs native Claude Code and the =claude-code-sandboxed= wrapper for running an agent *on* the box. Most repo users never need this — the stack works out of the box as =ops=.

**The core invariant:** live signing material (keystore password, wallet seed, vault password) is never held by any Claude-driven session — it is supplied human-in-the-loop at sign time. The propose/approve signer that enforces this for trades lives in the interop phase (see `docs/sandboxed-remote-access-handoff.md`).

**How bubblewrap isolation works:**
- Bubblewrap uses Linux namespaces (same foundation as containers)
- Mount tmpfs over `/home/dev/.secrets/` to hide it from sandboxed code
- Code sees a normal filesystem except `.secrets/` appears empty
- No modifications to the sandboxed program needed

**Prerequisites:** None — installs bubblewrap. =ops= access rides the existing wg0 SSH path (no new port); requires `ops_authorized_key` to be set (fails closed otherwise).

** Dev-mode on-box Claude Code (opt-in)

Gated on =dev_access_enabled= (default OFF). This installs a native Claude Code on the box plus the =claude-code-sandboxed= wrapper, for contributors who want to run an agent *on* the box. The default =ops= front door installs none of this — Claude runs on the laptop.

#+begin_src bash :tangle ../configs/templates/claude-code-sandboxed.sh.j2
#!/bin/bash
# Sandboxed Claude Code launcher
# Generated from org/14-sandbox.org

# Check if claude is available
if ! command -v claude &> /dev/null; then
  echo "Error: claude not found. Install with: curl -fsSL https://claude.ai/install.sh | bash"
  exit 1
fi

# Mount order matters: bwrap applies operations in sequence, so the .secrets and
# Chromium tmpfs overlays MUST come after the --bind of the home directory.
# If the home bind ran last it would re-expose the real (secret) contents.
exec bwrap \
  --ro-bind / / \
  --dev /dev \
  --proc /proc \
  --bind /home/{{ dev_user }} /home/{{ dev_user }} \
  --tmpfs /home/{{ dev_user }}/.secrets \
  --tmpfs /home/{{ dev_user }}/.config/chromium \
  --bind /tmp /tmp \
  --unshare-all \
  --share-net \
  --die-with-parent \
  claude "$@"
#+end_src

#+begin_src yaml :tangle ../ansible/fragments/14-sandbox.yml

** ops landing zone (sandboxed remote access)

Gated on =ops_access_enabled= (default ON). The laptop connects as =ops@box= over wg0; sshd forces every session through a bubblewrap =ForceCommand= jail. The =ops= uid is non-privileged, has no sudo, and is not in =wheel= — so it **cannot read** secrets owned by =dev=/root at =0700=, which is the real boundary. Bubblewrap is defense-in-depth: it reuses the =claude-code-sandboxed= mount set (KEEP IN SYNC) to blank the secret paths and narrow the filesystem.

The phase **fails closed**: if =ops_access_enabled= is true but =ops_authorized_key= is empty, the play aborts rather than creating an unreachable (or worse, mis-scoped) account.

*** ForceCommand jail wrapper

Runs =$SSH_ORIGINAL_COMMAND= (for =ssh ops@box "cmd"=) — or an interactive login shell when empty — inside bubblewrap. Mount order matches the dev wrapper: the tmpfs overlays come *after* the home =--bind= so they cannot be re-exposed.

#+begin_src bash :tangle ../configs/templates/ops-sandbox.sh.j2
#!/bin/bash
# ops sandboxed ForceCommand jail — landing zone for laptop-side Claude over wg0
# Generated from org/14-sandbox.org
#
# The real boundary is uid separation: ops cannot read {{ dev_user }}/root keys
# (0700, owned by another uid). bubblewrap is defense-in-depth — it blanks the
# secret paths and narrows the FS. Mount set KEEP IN SYNC with
# /usr/local/bin/claude-code-sandboxed and org/80-secrets-isolation.org.
set -euo pipefail

jail() {
  exec bwrap \
    --ro-bind / / \
    --dev /dev \
    --proc /proc \
    --bind /home/{{ ops_user }} /home/{{ ops_user }} \
    --tmpfs /home/{{ dev_user }}/.secrets \
    --tmpfs /home/{{ dev_user }}/.config/chromium \
    --bind /tmp /tmp \
    --unshare-all \
    --share-net \
    --die-with-parent \
    "$@"
}

if [ -n "${SSH_ORIGINAL_COMMAND:-}" ]; then
  # Non-interactive: ssh ops@box "some command"
  jail /bin/bash -c "$SSH_ORIGINAL_COMMAND"
else
  # Interactive PTY: ssh ops@box
  jail /bin/bash -l
fi
#+end_src

*** sshd drop-in for the ops principal

Arch's =sshd_config= =Include=s =/etc/ssh/sshd_config.d/*.conf=. This =Match User= block is net-new to the repo (access control was firewall-only until now). It pins =ops='s authorized key to a root-owned file outside =ops='s home (so =ops= cannot append keys), forces the jail wrapper, and strips forwarding/tunnelling.

#+begin_src bash :tangle ../configs/templates/sshd-ops.conf.j2
# Sandboxed remote-access principal — generated from org/14-sandbox.org
# Operate the box from a laptop over wg0 with the box's secrets kept invisible.
Match User {{ ops_user }}
    AuthorizedKeysFile /etc/ssh/authorized_keys.d/{{ ops_user }}
    ForceCommand /usr/local/bin/ops-sandbox
    AllowTcpForwarding no
    AllowAgentForwarding no
    X11Forwarding no
    PermitTunnel no
    PermitTTY yes
#+end_src

*** Provision the ops account, jail, and sshd policy

#+begin_src yaml :tangle ../ansible/fragments/14-sandbox.yml
    - name: Fail closed when ops access is enabled without an authorized key
      assert:
        that:
          - ops_authorized_key | default('') | trim | length > 0
        fail_msg: >-
          ops_access_enabled is true but ops_authorized_key is empty. Set the

          sandboxed remote-access front door.
      when: ops_access_enabled | bool
      tags: [sandbox, ops-access]

    - name: Create ops user (sandboxed, non-privileged, no sudo)
      user:
        name: "{{ ops_user }}"
        comment: "Sandboxed crypto-ops landing zone"
        shell: /bin/bash
        create_home: yes
        groups: []
        append: no
        password: '!'
      when: ops_access_enabled | bool
      tags: [sandbox, ops-access]

    - name: Deploy ops ForceCommand jail wrapper
      template:
        src: ../configs/templates/ops-sandbox.sh.j2
        dest: /usr/local/bin/ops-sandbox
        owner: root
        group: root
        mode: '0755'
      when: ops_access_enabled | bool
      tags: [sandbox, ops-access]

    - name: Create root-owned authorized_keys directory for ops
      file:
        path: /etc/ssh/authorized_keys.d
        state: directory
        owner: root
        group: root
        mode: '0755'
      when: ops_access_enabled | bool
      tags: [sandbox, ops-access]

    - name: Install ops authorized key (root-owned, outside ops home)
      copy:
        content: "{{ ops_authorized_key }}\n"
        dest: "/etc/ssh/authorized_keys.d/{{ ops_user }}"
        owner: root
        group: root
        mode: '0644'
      when: ops_access_enabled | bool
      tags: [sandbox, ops-access]

    - name: Deploy sshd drop-in for the ops principal
      template:
        src: ../configs/templates/sshd-ops.conf.j2
        dest: /etc/ssh/sshd_config.d/10-ops.conf
        owner: root
        group: root
        mode: '0644'
        validate: "/usr/sbin/sshd -t -f %s"
      when: ops_access_enabled | bool
      notify: reload sshd
      tags: [sandbox, ops-access]
#+end_src

*** Harden secret paths against the ops uid

The real wall is that =ops= cannot read another uid's keys. These tasks defensively assert =0700= on the secret directories (created by later phases) so a stray group/other bit never opens a hole, and skip cleanly when a directory does not yet exist.

#+begin_src yaml :tangle ../ansible/fragments/14-sandbox.yml
    - name: Stat dev secret paths
      stat:
        path: "{{ item }}"
      loop:
        - "/home/{{ dev_user }}/.secrets"
        - "/home/{{ dev_user }}/.foundry/keystores"
      register: ops_secret_paths
      when: ops_access_enabled | bool
      tags: [sandbox, ops-access]

    # Enforce 0700 only where the path already exists — do not pre-create
    # .secrets here (phase 80 owns its creation/migration).
    - name: Enforce 0700 on existing dev secret paths (defense against ops reads)
      file:
        path: "{{ item.item }}"
        state: directory
        owner: "{{ dev_user }}"
        group: "{{ dev_user }}"
        mode: '0700'
      loop: "{{ ops_secret_paths.results | default([]) }}"
      loop_control:
        label: "{{ item.item }}"
      when:
        - ops_access_enabled | bool
        - item.stat is defined
        - item.stat.exists | default(false)
      tags: [sandbox, ops-access]
#+end_src

** Notes

*** How Sandboxing Works

Bubblewrap creates a new namespace where:
- Most filesystem is read-only bind-mounted
- `/home/dev/projects` is bind-mounted read-write (for Claude Code edits)
- `/home/dev/.secrets/` is replaced with empty tmpfs
- App sees everything except secrets

*** ops remote access (the default front door)

From the laptop, over wg0 — the box installs no agent for this; Claude runs locally and drives the box via SSH:

#+begin_example
# Run a single command in the jail
ssh ops@<box>.local "cast --version"

# Interactive shell inside the jail
ssh ops@<box>.local
#+end_example

Every =ops= session is forced through =/usr/local/bin/ops-sandbox= (bubblewrap), runs as a non-privileged uid with no sudo, and cannot read =dev=/root secrets. The propose/approve signer for trades is added in the interop phase (PASS 2).

*** dev on-box Claude Code Usage (opt-in)

#+begin_example
