## Project Overview

Literate Monero is a **literate programming** project where Emacs org-mode files (`org/`) ARE the source code. Documentation and infrastructure code are unified — every change to the system requires editing the narrative `.org` files, which are then **tangled** (extracted) into executable Ansible playbooks and shell scripts.

Target: Omarchy Linux (Arch-based).

The core is a full sovereign Monero node with privacy networking (Tor/I2P), mining (P2Pool/XMRig), and WireGuard VPN. More broadly, the project is a **sovereign, privacy-first crypto stack anchored by Monero**: beyond the Monero-native core it adds opt-in, off-by-default phases — a Monero-native exchange, and an **interop** tier for interacting with external (non-Monero) chains the same way (self-hosted, sandboxed, Tor-routed, auditable). Monero is the anchor and the signal of intent, not a hard scope boundary — the test for any component is whether it advances sovereign, private operation with no trusted third parties. Some components (the interop edge especially) are included not because they are maximally private, but because they are the least-leaky way to do a thing you need.

## Security Context

This repository handles sensitive credentials (cryptocurrency keys, SSH keys, VPN configs).

**When suggesting changes:**
- Flag any network operations to external hosts (curl, wget, git clone)
- Never add dependencies without explicit user approval  
- Document all credential/key handling clearly
- Avoid "convenience" features that bypass user review
- Assume the user can audit Org-mode and Ansible

The literate programming approach means users read the source. Maintain that transparency.


## Build Commands

```bash
# Generate all playbooks from org files (requires Emacs)
make all

# Alternative: tangle everything via script
./tangle.sh

# Clean generated files
make clean

# Show dependency graph
make show

# Initial system setup (installs Emacs, Ansible, tmux)
./bootstrap.sh

# Validate configuration before deployment
ansible-playbook ansible/validate.yml

# Deploy a specific phase
ansible-playbook ansible/playbook.yml --tags <phase> -K

# Syntax check
ansible-playbook ansible/playbook.yml --syntax-check

# Dry run with diff
ansible-playbook ansible/playbook.yml --check --diff -K
```

## Architecture

### Tangling Pipeline

```
org/*.org  →  (emacs org-babel-tangle)  →  ansible/fragments/*.yml
                                            ansible/group_vars/all.yml
                                            ansible/ansible.cfg
                                            ansible/inventory.yml
                                            ansible/validate.yml

ansible/fragments/*.yml  →  (assemble-playbook.sh)  →  ansible/playbook.yml
```

The Makefile tracks dependencies between org files and their generated fragments, only re-tangling what changed. `config.yml` is a dependency of all phase fragments.

### Phase Names and File Numbering

**Refer to phases by name** (their Ansible tag: `privacy`, `monerod`, `users`, `wallet`, `mining`, `firewall`, …), not by number. The numeric file prefixes exist only to define execution order and may be renumbered when phases are restructured; names are stable.

- `00-configuration.org` → Ansible config files + `group_vars/all.yml`
- `01-validation.org` → Pre-flight validation playbook
- `10`–`19` range → Installation phases (base system → mining), executed sequentially
- `20-exchange.org` → Opt-in Monero-native exchange (RetoSwap/Haveno), off by default
- `30-interop.org` → Opt-in interop tier, off by default — first tier beyond the Monero-native core. Two independently-gated components: `cast` (Foundry) EVM CLI signer over Tor (`cast_enabled`), and the Rabby browser-extension dapp-UI fallback on the Mullvad path (`rabby_enabled`)
- `80`–`84` range → Post-install phases (secrets, firewall, monitoring, backup, verification)
- `97-updates.org` → Version upgrade management
- `98-handlers.org` → Ansible handlers (service restarts, reloads)
- `99-appendix.org` → Reference only, excluded from tangling pipeline

### Key Dependencies Between Phases

- Privacy requires the base system
- Monerod requires the privacy services for I2P networking
- Mining requires monerod for blockchain data
- Interop requires privacy and the sandbox hardening posture, but NOT monerod/mining — EVM interop is independent of the Monero node. `cast` uses the Tor path; the Rabby fallback reuses the privacy phase's fail-closed Mullvad browser path (it sets `MULLVAD_BROWSER_PROFILE` to open a dedicated `wallet` profile through the same kill-switch)
- Firewall depends on all service installations being complete

### Generated vs Source Files

**Never edit directly** — these are generated by tangling:
- `ansible/playbook.yml`
- `ansible/validate.yml`
- `ansible/fragments/*.yml`
- `ansible/group_vars/all.yml`
- `ansible/ansible.cfg`, `ansible/inventory.yml`

**Edit these** — source of truth:
- `org/*.org` files
- `config.yml` (user configuration)
- `configs/templates/*.j2` (Jinja2 templates)

## Code Conventions

- Discuss approach before generating complete implementations
- Refer to phases by name, not number, in docs, comments, and commands (numbers are just file ordering)
- Use conventional commit format with co-author attribution
- Shell scripts use `set -euo pipefail` and color-coded output
- Org code blocks must preserve indentation (`org-src-preserve-indentation t`)
- Ansible YAML fragments must maintain consistent structure for assembly
